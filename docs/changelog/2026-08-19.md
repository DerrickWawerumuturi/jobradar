# 2026-08-19

Fixed skill-extraction quality, aligned the CV and job skill vocabularies,
added a health endpoint, unblocked the event loop, and cut analysis time from
~297s to ~44s.

---

### File
`src/Agent/utils/skill_extractor.py`

### What changed

Rewritten to emit canonical EMSI skill names, strip non-requirement text before
extraction, deny known false matches, and propagate failures instead of
swallowing them. Added `normalize()` for CV skills.

### Why

Extraction returned lemmatiser-mangled text (`big datum`, `machine learn`,
`problem solve`) and false positives (`San` from "San Jose", `com` from a URL,
`e` from "e.g.", `nice` from "Nice to Have"). The most-demanded "skill" was
`software engineer`. Every chart built on this output was meaningless.

### How it works

SkillNer reports `doc_node_value` — the matched span from its *preprocessed*,
lemmatised text. Every match also carries a `skill_id`, so the canonical name is
now looked up from `SKILL_DB[skill_id]["skill_name"]` instead.

Two denylists filter what remains: `DENYLISTED_SURFACE_FORMS` for abbreviation
collisions with ordinary prose, and `DENYLISTED_SKILL_NAMES` for real database
entries that are job titles or fields of study.

`prepare_description()` runs `_strip_boilerplate` (legal, benefits, company
culture) then `_focus_on_requirements` (keeps requirements-style sections plus
the two blocks after each heading), falling back to full text if under 400
characters survive.

### Before → After

```
big datum                  →  Big Data
machine learn              →  Machine Learning
object orient programming  →  Object-Oriented Programming (OOP)
node js                    →  Node.js
react                      →  React.js
San, com, e, nice, los     →  removed
software engineer          →  removed (job title, not a skill)
```

### Dependencies / relationships

Its output is the vocabulary for `MarketAnalyzer` and the embeddings, so every
number in the dashboard changes when this changes.

### Design decisions

`c`, `r` and `go` are deliberately absent from the surface-form denylist — they
are genuine languages that a naive minimum-length rule would delete.

Failures propagate rather than returning an empty set. See the `parser.py` entry
for why that mattered.

`en_core_web_sm` was rejected as a faster alternative: it ships without word
vectors, and SkillNer's n-gram scorer calls `token.similarity()`, which would
silently degrade to noise. The expensive path carries the most important
matches.

### Learning notes

When a library exposes both a matched surface form and a stable identifier, the
identifier is the reliable one — the surface form reflects whatever
preprocessing happened to be applied.

### File
`src/Agent/Framework/JobRadarAgent.py`, `src/Agent/Framework/SimilarityEngine.py`

### What changed

CV skills are normalised through the same extractor as job skills before market
analysis. Skill matching became case-insensitive while preserving canonical
casing for display.

### Why

CV skills come from the LLM as free text (`react`, `aws`); job skills come from
SkillNer as canonical names (`React.js`, `Amazon Web Services`).
`MarketAnalyzer` compared them by exact string, so the two sides were matched
across different vocabularies — understating coverage and inventing gaps.

### How it works

`skill_extractor.normalize()` maps each CV skill onto the canonical vocabulary,
keeping unrecognised skills verbatim so nothing is silently dropped.
`calculate_skill_frequency` counts on a lowercased key but emits the canonical
spelling; the three membership tests compare on `.lower()`.

### Design decisions

The bug predated canonical names — `aws` never matched `amazon web service`
either — but adopting canonical names would have made it far worse, so both
changes had to land in the same commit.

### Learning notes

Exact string matching between two independently produced label sets fails
silently rather than erroring. Any cross-source comparison needs an explicit
shared vocabulary.

### File
`src/Agent/utils/extraction_pool.py` (new), `src/Agent/utils/parser.py`

### What changed

Skill extraction moved to a process pool with a warm extractor per worker.
Postings whose extraction fails are dropped and logged rather than kept with an
empty skill list.

### Why

Profiling showed extraction was **251.7s of a 269.5s** analysis — 93% of
runtime — running single-threaded over every posting in sequence.

Separately, SkillNer raises on some inputs (`'improve' is not in list`,
`list index out of range`). Those three postings out of twenty-two were kept
with zero skills and still counted toward `jobs_analyzed`, deflating every
frequency by roughly 14%.

### How it works

`ExtractionPool` lazily creates a `ProcessPoolExecutor` whose initializer builds
one `SkillExtractor` per worker, kept warm for the process lifetime.
`parse_retrieved_jobs` submits all descriptions at once and drops any result
that returned `None`.

### Design decisions

Processes, not threads: the work is pure CPU so the GIL blocks any thread gain,
and spaCy pipelines are not safe to call concurrently on one object.

Worker count is `min(4, cpus - 1)`, overridable via
`JOBRADAR_EXTRACTION_WORKERS`. The cap is a memory bound — each worker holds its
own `en_core_web_lg` and the 31k-entry matchers — not a core bound.

`parse_retrieved_jobs` lost its `skill_extractor` parameter; it now uses the
pool directly.

### Learning notes

Parallelism only helps where the time actually is. Measuring first showed every
other stage combined was under 18 seconds, so optimising anything else would
have been wasted effort.

### File
`src/Agent/Framework/SearchEngine.py`

### What changed

Provider and per-country requests now run concurrently, and every HTTP call has
a timeout.

### Why

`JSearchProvider` looped three countries with a blocking request each, then Muse
ran after that — four sequential round trips (14.8s) for independent calls. None
had a timeout, so one unresponsive provider could stall an analysis
indefinitely.

### How it works

Countries fan out in a `ThreadPoolExecutor` inside the provider; providers fan
out in another at the `SearchEngine` level, so all four upstream requests
overlap. `REQUEST_TIMEOUT = (5, 30)` applies to every call.

### Design decisions

Threads are correct here, unlike for extraction — this is network wait and the
GIL is released during I/O.

`except ValueError` was widened to `except Exception`. A `Timeout` or
`ConnectionError` is not a `ValueError`, so those handlers could never have
caught the failures they were written for.

### Learning notes

An exception handler is only as useful as the types it names. Guarding network
calls with `except ValueError` reads as error handling while catching nothing
that actually occurs.

### File
`main.py`

### What changed

Added `GET /health`, moved analysis work off the event loop, and serialised
analyses behind a lock.

### Why

`/analyze` was declared `async def` but called synchronous work directly,
pinning uvicorn's event loop. The entire API was unreachable for the several
minutes each analysis took, so the dashboard could not poll for liveness.

### How it works

```python
async with analysis_lock:
    cv_text = await run_in_threadpool(pdf_inspector.extract_text, temp_path)
    result  = await run_in_threadpool(job_radar_agent.run, cv_text)
```

### Before → After

Health probes during a live analysis went from timing out to answering in
1–16ms, measured across a full 297s run.

### Design decisions

The lock is required *because* of the threadpool change. Offloading made the
endpoint concurrent, and `job_radar_agent` holds a single shared
`SkillExtractor` wrapping a shared spaCy pipeline, which is unsafe to call from
two threads. Analyses queue; every other endpoint stays responsive.

Genuine parallel analyses would need a pipeline instance per worker or multiple
uvicorn workers — a larger change than removing the lock.

### Learning notes

`async def` does not make a function non-blocking. It only marks it awaitable;
synchronous work inside it still occupies the event loop and stalls every other
request in the process.

# Persistent job storage

Jobs are no longer discarded after a request. Every posting a provider returns
is stored in Postgres, deduplicated on `(provider, external_id)`, with its raw
payload retained and its extracted skills written to a normalized skill graph.

The analysis pipeline is unchanged and the `/analyze` response contract is
additive-only. See `decisions/persistent-job-storage.md` for the reasoning
behind every choice below.

---

### File
`src/database/` (new package)

### What changed

A storage layer in four parts: `session.py` (pooled connections),
`migrate.py` + `migrations/*.sql` (schema), `repositories/` (SQL), and
`services/ingestion.py` (the single entry point the pipeline calls).

Four migrations create `jobs`, `searches` + `search_provider_runs`,
`skills` + `job_skills`, and `job_observations`.

### Why

Every analysis re-bought the same postings from the same APIs and kept nothing.
Questions about how the market *changes* — skill demand over time, posting
lifetime, provider quality, skill co-occurrence — cannot be answered
retroactively, so the cost of not starting compounded daily.

### How it works

`jobs` holds source data only: provider values verbatim, plus the complete
`raw_payload` as `jsonb`. Nothing JobRadar derives is stored there — that lives
in `job_skills`. The split is a table boundary, not a naming convention.

Writes go through a single batched upsert:

```sql
insert into jobs (...) values (...), (...)
on conflict (provider, external_id) do update set
    last_seen_at = now(),
    title        = coalesce(excluded.title, jobs.title),
    ...
returning id, provider, external_id, (xmax = 0) as inserted
```

`coalesce(excluded.x, jobs.x)` stops a thinner later response nulling out data
we hold; `first_seen_at` is absent from the update list so it cannot move; the
longer description wins because providers truncate inconsistently.
`xmax = 0` separates inserts from updates, which is where a real duplicate rate
comes from.

### Design decisions

Raw SQL migrations rather than SQLAlchemy/Alembic. The central operation is an
`ON CONFLICT DO UPDATE … RETURNING`, clearer as SQL than as ORM calls, and the
later ML work reads via `pandas.read_sql`, which wants no ORM. The cost —
hand-written row mapping, no autogenerated diffs — was accepted deliberately.

`prepare_threshold=None` on runtime connections. `DATABASE_URL` is Neon's
`-pooler` host, which is PgBouncer in transaction mode; psycopg auto-prepares a
statement after its fifth execution, and the next transaction may land on a
different backend. That produces intermittent `prepared statement already
exists` under load and nowhere else.

Migrations use `DATABASE_URL_DIRECT` (the same host without `-pooler`), because
DDL and `CREATE EXTENSION` want a real session rather than PgBouncer.

### Learning notes

A connection string is part of the architecture. The `-pooler` suffix changes
which Postgres features are safe to use, and nothing in the code makes that
visible — it has to be known.

### File
`src/Agent/utils/types.py`

### What changed

`Job` gained `provider`, `external_id` and `raw` (all `Field(exclude=True)`),
four `salary_*` fields, `posted_at_utc`, and a validator that coerces integer
ids to strings.

### Why

**The Muse contributed zero jobs.** `Job.id` was typed `str | None`, The Muse
returns integer ids, and pydantic 2 does not coerce `int` to `str`:

```
Job(id=12345) -> ValidationError: Input should be a valid string
```

`MuseProvider.search` caught `ValidationError` and printed "Skipping invalid
job" for every posting, so JSearch was silently the only live provider. The
handler made a total failure look like routine per-record noise.

Separately, `(provider, external_id)` could not be assembled at all: no field in
the codebase held a provider name, and `raw` was destroyed inside `parse_job`.

### How it works

The three persistence fields are `exclude=True`, so they are available in-process
and absent from the `/analyze` response. Verified through FastAPI's encoder with
`ProcessedJob` nesting, not just `model_dump()`.

### Design decisions

`posted_at` keeps its existing meaning — whatever the provider called it, which
for JSearch is `"2 days ago"` — and `posted_at_utc` was added alongside for the
absolute value. Repointing `posted_at` would have silently changed what the
dashboard renders.

### Learning notes

An exception handler that fires on every record is not error handling, it is a
disabled feature with a log line. "Skipping invalid job" printed 20 times per
run reads as tolerable noise and was total data loss.

### File
`src/Agent/Framework/SearchEngine.py`

### What changed

Providers declare a `name`; `parse_job` stamps provider, external id and raw
payload; `search()` takes an optional `run_log`; several field mappings were
corrected.

### Before → After

```
url          employer_website  →  job_apply_link
salary       job_salary        →  job_max_salary  (job_salary is not a JSearch field)
salary_min   —                 →  job_min_salary
salary_max   —                 →  job_max_salary
currency     —                 →  job_salary_currency
posted_at_utc —                →  job_posted_at_datetime_utc
muse level   —                 →  levels[0].name
muse type    —                 →  type
muse posted  —                 →  publication_date
```

`employer_website` is the company's homepage, so it was identical for every
posting at that employer — and the original scaffold schema deduped on
`url unique`, which would have collapsed an entire employer into one row.

Muse's `levels[0].name` is the only source of `experience_level` in the whole
pipeline. It is provider-supplied, not inferred.

### How it works

`name` lives on the `JOBPROVIDER` base class and is applied in `parse_job`, so a
new provider cannot forget to set it. `run_log` is an out-parameter — the engine
appends one entry per upstream request (status, params, timing) and knows
nothing about storage.

### Design decisions

`except requests.Timeout` was split out from the general handler so a timeout is
recorded as `'timeout'` rather than `'exception'`. Provider reliability is one
of the things this data is meant to measure, and the distinction is lost if
every failure has the same label.

### File
`src/Agent/Framework/JobRadarAgent.py`

### What changed

Three fail-soft persistence calls inserted around the existing pipeline.

```python
raw_jobs  = self.search_engine.get_jobs(query, run_log=run_log)
search_id = self.ingestion.record_search(query, run_log, len(raw_jobs), started_at)
job_ids   = self.ingestion.persist_jobs(search_id, raw_jobs)
jobs      = parse_retrieved_jobs(raw_jobs)          # unchanged
self.ingestion.persist_skills(job_ids, jobs)
```

### Why

Persistence belongs to the orchestrator, not to `SearchEngine` (which retrieves)
or `MarketAnalyzer` (which analyses). Neither knows a database exists.

Raw postings are stored *before* parsing, so the ones `parse_retrieved_jobs`
discards — no description, or a SkillNer failure, roughly 14% of a run — now
enter the dataset and stay reprocessable instead of being lost.

### Design decisions

`job.raw` is cleared after persistence. It has served its purpose, nothing
downstream reads it, and FastAPI's encoder deep-copies dataclass fields before
serialising — so leaving 40 payloads attached would have been pure waste.

Every persistence call is wrapped, and the first failure pauses writes for 60
seconds. Measured: with the database unreachable, an analysis completed
normally, and the breaker cut the added latency from 20s to 10s.

### Learning notes

Fail-soft is not just `try/except`. Without the cooldown, each call paid the
full pool timeout independently, so "degrade gracefully" still meant a 20-second
penalty on every analysis.

Ran against the live Neon schema with synthetic postings covering each path:

| Check | Result |
|---|---|
| Muse integer id | parsed, stored as `'987654'` |
| Muse `experience_level` | `'Mid Level'` — first non-NULL in the pipeline's history |
| In-batch duplicate | 4 postings parsed → 3 rows |
| Second identical run | `jobs` unchanged at 3; `last_seen_at` moved, `first_seen_at` did not |
| Observations | 3 → 6 across the two runs |
| Skills | 5 links, unchanged on re-run |
| Missing provider id | `fp:ed3eecee…`, `identity_source='fingerprint'` |
| Payload drift | observation flagged `payload_changed`, kept a copy; longer description won |
| Migration re-run | "Schema up to date" |
| Database unreachable | analysis completed, nothing raised, 10s added |
| `raw` in API response | absent, verified through FastAPI's encoder |

Test rows were truncated afterwards; the tables are empty.

## Not done — deliberately

- **Phase 6, embeddings in pgvector.** Separate concern from collecting the
  dataset. `jobs.id` is a stable FK whenever it starts.
- **Phase 7, any model.** There is no label to train on. `overall_score` is a
  fixed weighted cosine, so a model fitted to it re-learns arithmetic we already
  have in closed form — and two of its four terms are near-constant across
  postings. Real labels need saved/applied/dismissed events from the dashboard,
  which does not emit them yet.
- **Cross-provider duplicate merging.** `fingerprint` is indexed on every row so
  this stays possible without an API backfill.
- **`skills.emsi_skill_id`.** `SkillExtractor` discards the id it matched on;
  threading it out would change `extract()`'s return shape.
