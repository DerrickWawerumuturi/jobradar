# 2026-08-21

Made the search follow the user's actual location. JobRadar searched three
hardcoded countries; a user in Nairobi got the American job market.

Full reasoning in `decisions/location-aware-search.md`.

---

### File
`src/Agent/utils/location.py` (new)

### What changed

Resolves the LLM's free-text location into validated provider parameters, and
judges whether a remote posting will hire from the user's country.

### Why

`query.location` was extracted correctly by the LLM and then dropped. Grep found
it used in `embedder.py` and `SimilarityEngine` only — it influenced *ranking*
and never *retrieval*, so JobRadar ranked American jobs by how well they matched
a Kenyan address.

### How it works

The model is asked for `country_code` (ISO alpha-2) and `city` directly, since
mapping "Nairobi" to a country needs world knowledge a local table lacks. The
answer is then corroborated against the free-text location, and the text wins on
conflict.

### Design decisions

**Validating the code against the ISO list is not enough.** The first version
did that and accepted `country_code="kn"` for `"Nairobi, Kenya"` — Saint Kitts
and Nevis, a valid code. A hallucinated code is almost always a valid code for
the wrong country, so only corroboration catches it.

`remote_eligibility` returns `True`/`False`/`None`, and the `None` is
load-bearing — see the SearchEngine entry.

### Learning notes

"Is this well-formed?" and "is this correct?" are different questions. Format
validation feels like verification and catches almost nothing when the error
source is a language model.

### File
`src/Agent/Framework/SearchEngine.py`

### What changed

Rewritten around `SearchScope`. Two legs per search — `local:<country>` and
`remote:global` — with providers declaring which legs they can serve. Added
Remotive, RemoteOK and Jooble. Added dedup, an eligibility filter, and a
minimum-jobs floor.

### Before → After

Every row below was measured against the live API:

```
query="… in ke"              1 job    →  query="… in Kenya", country=ke   10 jobs
query="… in gb"              0 jobs   →  query="… in United Kingdom"      10 jobs
muse category="ml engineer"  total=0  →  category="Software Engineering"  100,852
remoteok tags="ml engineer"  0 jobs   →  tags="machine learning"          24 jobs
```

The `gb` result is the notable one: the old loop interpolated the ISO code into
the query text and passed no `country` parameter, so **the UK leg had been
returning nothing** for as long as it existed.

### How it works

The ISO code goes in `country`; a real place name goes in the query text.
Providers declare `scopes`, so remote-only boards are never asked for jobs in
Nairobi. Every leg runs concurrently.

Muse's `location` filter narrows its corpus without restricting it — asking for
Nairobi still returns Dallas — so returned locations are re-checked for local
legs. Muse's `category` is validated against its taxonomy first; no category
beats a wrong one.

### Design decisions

**Two legs, not one.** Someone outside the large markets has two markets, and
the remote half is usually the larger. Local-only hides most of their
opportunities; global-only is what the hardcoded list already did.

**`None` is not `False` in eligibility.** The first implementation treated an
absent eligibility string as a restriction and discarded *every* RemoteOK
posting, since that board leaves the field blank. Unknown and excluded are
different answers.

**The floor is measured after filtering.** 17 postings cleared a floor of 15,
then reduced to 8 once US-only remote jobs were dropped — under the floor with
nothing widened. It now runs on the count that actually reaches the analysis.

**Dedup added.** Legs overlap, and `MarketAnalyzer` counts skills per job, so a
duplicate inflates every skill that posting mentions rather than merely
repeating in the list.

### Learning notes

A parameter accepted without error is not a parameter honoured. Muse returns
`200 OK` and a full page for a category that matches nothing, and for a location
it does not enforce. Both had to be measured, not read.

### File
`src/Agent/utils/types.py`, `src/Agent/utils/prompts.py`

### What changed

`ParsedQuery` gained `country_code`, `city` and `category`. `Job` gained
`remote_eligibility`. The prompt asks for ISO codes and the correct Muse
taxonomy.

### Why

`category` is the interesting one: **the prompt had always asked for it and
`ParsedQuery` had no such field**, so pydantic silently discarded it and
`MuseProvider` fell back to sending the job title — which matches nothing in
Muse's taxonomy. The prompt's suggested values were also wrong; "Data Science"
has 2 postings where "Data and Analytics" has 18,401.

### Learning notes

A prompt that asks for a field the schema does not declare fails silently in
both directions: the model pays to produce it, and the code never sees it.

### File
`src/Agent/Framework/JobRadarAgent.py`, `src/database/migrations/005_search_location.sql`

### What changed

`get_jobs` returns a `SearchOutcome`, and `/analyze` gained a `search` block
reporting resolved location, legs run, whether the floor widened the search, and
per-provider status. `searches` gained `country_code`, `city`, `scopes`,
`widened`; `jobs` gained `remote_eligibility`.

### Why

A six-job analysis and a forty-job one look identical to the dashboard, and the
frequencies in `market` mean very different things in each.

## Not done

- **JSearch quota is exhausted.** Spent during the coverage probing in this
  session. It will fail until the plan resets, and `search_provider_runs` now
  records every 429.
- **Jooble is implemented but disabled** pending `JOOBLE_API_KEY`. It is the
  only provider here with real inventory outside the large markets, so local
  Kenyan coverage effectively depends on it. Its `snippet` is truncated — the
  reason Adzuna was dropped — so measure extraction quality before trusting it.
- **Remotive returns its whole inventory.** `search=`, `category=` and no
  parameters all return the same 17 postings, including "Patient Care
  Specialist" for a machine-learning query. Those count equally in
  `MarketAnalyzer`. No relevance filter was added, because defining relevance
  changes what "the market" means.
- **City-only hallucination is not caught.** "Nairobi" with `country_code="kn"`
  has nothing to corroborate against; that needs a city→country dataset.
- `location_score` weighting was not revisited, though the facet now carries
  real signal for the first time.
